# CLAUDE.md

Project-level instructions for Claude Code sessions in this repository. These persist across sessions; treat them as durable user preferences.

## Workflow

### Pull requests

- **Always squash-merge a PR you opened once its CI is green.** Don't wait for explicit approval each time. If CI fails, investigate the failure rather than merging anyway.
- Open PRs as **drafts** by default; flip to ready when CI passes (squash-merge implies ready).
- One concern per PR. If a follow-up touches different files / different reviewer focus, open a separate PR rather than tacking it onto the current one.
- Reply to AI review comments (Gemini etc.) only when the suggestion is being declined or when noting a fix landed in a specific commit. Skip routine "fixed it" replies on threads that are already self-evident.

### Branches

- Feature branches: `claude/feature/<short-kebab-summary>`
- Fix branches: `claude/fix/<short-kebab-summary>`
- Docs and chores: `claude/docs/<…>`, `claude/chore/<…>` (a release bump is `claude/chore/release-<version>`).
- Always branch off latest `origin/main`, not whatever the working tree happens to be on.

### Commits

- Conventional-commit prefixes: `feat:`, `fix:`, `ci:`, `chore:`, `docs:`, `test:`, `refactor:`. Scope optional (`feat(ai): ...`).
- Each commit message ends with the session footer:
  ```
  https://claude.ai/code/session_<id>
  ```
  where `<id>` is the current session id (substituted by the harness at write time).

### Research

- Browse the web freely for any research: library and API docs, platform behaviour, prior art, model pricing, bug reports upstream. Prefer primary sources (official docs, specs, source code, release notes) and cite the URLs in the PR or issue that relies on them.

## Repo specifics

- Tauri 2 desktop app under `apps/desktop/`. Frontend in `apps/desktop/src/`, Rust backend in `apps/desktop/src-tauri/`.
- Architecture decisions are recorded in `docs/adr/` (one record per decision; read the record for an area before reshaping it, and supersede a record with a new one rather than editing it); domain terms are defined in `GLOSSARY.md`.
- Workspace crates under `crates/`: `ai` (LLM provider abstraction and agent loop), `tools` (the agent's audio editing tools — `docs/tools-reference.md` is generated from them), `audio-engine` (render), `audio-time` (phase vocoder), `session` (the node graph), others.
- Multi-provider LLM support: Anthropic, OpenRouter, OpenAI, Groq, Gemini and Ollama (local, no key). The `LlmProvider` trait in `crates/ai/src/provider.rs` is the extension point — request serialization + SSE parsing are per-provider. So is how much of the tool list a request carries (`tool_set()`): Ollama sends `ToolSet::Slim` (`crates/ai/src/tool_selection.rs`: a core list plus the tools the message names, the assistant just proposed or the user named earlier, compacted, within a byte budget, picked once per turn, with the names of the rest in one line of the system prompt so the model knows they exist; when the session block had to be cut, `list_session` is pinned into the set outside the tool budget, so the model can page through what the block left out, #618); every other provider sends all permitted tools, and Anthropic must, for its prompt cache. `crates/ai/tests/request_size.rs` bounds the slim request and ratchets the full one's system and tool sizes (`cargo test -p ai --test request_size -- --nocapture` prints them).
- The session block in the system prompt (`crates/ai/src/session_context.rs`: head, tracks, buses, master chain, selection, markers) is written within a byte budget (`block_budget`, #573): `SESSION_BLOCK_MAX_BYTES` (8,000 B) for a provider sent every tool, `SLIM_SESSION_BLOCK_MAX_BYTES` (2,300 B) for Ollama, whose block also shares the request with the tools (what it takes past `SLIM_SESSION_ALLOWANCE_BYTES` comes off the slim tool budget). A session that fits is written in full. One that does not has its track, bus and marker lists cut, and each cut list ends with a line that says how many were left out and names `list_session` (`crates/tools/src/tool/list_session.rs`, read-only so Plan first never holds it), which pages through the same lines: `tools::session_lines` writes them once for both, so the block and the tool cannot disagree (#618, #634). `crates/ai/tests/request_size.rs` runs a thirty-track and a two-hundred-track session and holds every session's first request `SESSION_HEADROOM_BYTES` under the bound, so a change that grows the block, a tool schema or the names line moves those numbers: run it.
- Per-provider keychain slots: `<provider_id>_api_key`, `<provider_id>_model`, `<provider_id>_base_url`, `<provider_id>_effort`, plus an `active_provider` slot. Anthropic's slot is `anthropic_api_key`, the name builds before multi-provider used, so old keys are found with no migration. On Linux the store is the Secret Service (GNOME Keyring, KWallet or KeePassXC), with the kernel keyring as the fallback for the current boot only when none is running; `get_keychain_persistence` reports which applies and the app shows a banner (#394). `has_api_key` rejects when the keychain cannot be read — that is not the same as `false`. The commands that write a slot (`set_api_key`, `set_api_key_for`, `set_active_provider`, `set_base_url_for`, `set_effort_for`, `set_active_model`) answer with the same `{ persistent, reason }` for the save they made, so a service that went away after launch is not silent: Settings shows the banner's text (`lib/keychainNotice.ts`) and holds the dialog open on **Continue** (#539). After a startup the keychain refused (`AppState::keychain_refused`), `rebuild_agent_into` makes no keychain read and builds no agent until a key or provider save lifts the refusal; `send_message` says why.
- App version is canonical in `apps/desktop/src-tauri/tauri.conf.json` — the `package.json` files and Cargo's `[workspace.package] version` mirror it, and `appVersion.test.ts` fails if they drift.
- Bundled skills (`apps/desktop/src-tauri/resources/skills/*.md`) are kept current in `~/.edytlab/skills/` by `bundled_skills.rs` (#574, #631), which the window runs at every launch (`install_bundled_skills`). `~/.edytlab/skills/.bundled.json` records the SHA-256 of the text it installed for each file: a file that still matches is replaced when the bundled text changes, an edited one is left alone and the new text is written beside it as `<name>.bundled.md` (the loader and the Skills editor skip that name), and a deleted one is not reinstalled. To change a bundled skill, edit its file and nothing else.

A verified, resumable model downloader (`ml_pipeline::fetched_model_path`) and the runtime gate below landed under #383, and one model is pinned (`whisper-base`, about 139 MB: three files of `onnx-community/whisper-base_timestamped` at a fixed commit, with size and SHA-256 each, in `crates/ml-pipeline/models.json`). **The app downloads it only when the user clicks Download in Settings → Account** (`download_ml_model`, with Cancel, resume and Remove beside it, #383 PR 6); nothing downloads by itself, not at launch, not when Settings opens, not from a tool or the agent (once #384 makes a tool use a model, it will find it with `ml_pipeline::models::cached` and report it is not downloaded when it is missing, and never fetch it; no tool uses a model yet), and `crates/ml-pipeline/tests/only_the_user_downloads.rs` and `speechModelOnlyOnClick.test.ts` fail if another path could. The download runs on its own thread and holds no store, engine, dispatcher or agent lock, and keeps the model under `app_local_data_dir()/models` (not the roaming `app_data_dir()`). No inference uses the file until #384, so "downloaded" is not "transcription works", and the Settings row says so. Don't write that the app downloads speech models automatically or on first use, and keep every copy of the privacy facts (GET requests to huggingface.co on the click, one per file and more on a retry; your IP address, the file requested and that edytlab, with its version in the User-Agent, is asking; no audio; no telemetry) in step: the privacy page, the local-first table, the press kit. - Anything that builds an `ort` session calls `ml_pipeline::runtime::ensure()` first. With `load-dynamic`, `ort` 2.0.0-rc.13 returns an error from `ort::init_from` when it cannot load the ONNX Runtime library (rc.12 deadlocked there and in every other entry point), but its implicit load, which `Session::builder` and `ort::api()` do on first use, panics (a release build aborts, and tools run while the agent loop holds the store and engine locks), and a bare or relative path goes to the system loader's search instead of failing. `ensure()` finds the library by absolute path and checks it before `ort` sees it. It looks in `ORT_DYLIB_PATH`, then the bundle directory the app registers at startup (`runtime::set_bundle_dir`, once: `Contents/Frameworks` on macOS, Tauri's resource directory on Linux, none on Windows), then next to the executable; on macOS older than `min_macos` in `ml-runtime.json` it answers `RuntimeUnsupported` before opening the file. The `ml_runtime_status` command and the Settings line report what it found (`edytlab-desktop --ml-runtime-status` prints the same answer as JSON with no window). Every release installer since v0.7.0 (the first after v0.6.1) carries ONNX Runtime 1.23.2 and its notices (and on Windows the four VC++ runtime DLLs it imports, `vc_runtime` in `ml-runtime.json`), so an installed build says bundled; a build from source has none and says not installed in this build. That carries no model and runs no inference.
- Undo/redo follow the path the user took (`apps/desktop/src/lib/headTrail.ts`, held by `useSession`), never `node.parent` alone. Node ids hash state only, so a revisited state keeps its first parent (#398). Every frontend head move must go through `setHeadLocal` (edits, agent, graph) or `resetHead` (opening a project). `GraphView` never calls `set_head_to` itself (Set as head goes through App's `onSetHead`), and anything showing session state re-reads on a `head` change, since `set_head_to` emits no event. The History graph reads again on `useSession`'s one `graphVersion` (#602): a head move or a project opening, `agent://done` (a `name_node` label moves no head), and every `forgetRemoved` (a compaction ending, a refused undo). `GraphView` gets it as `refreshKey` and reads nowhere else but its own rename; a preview click is none of these. A click on a graph bubble is a preview, not a head move (#522): it lives in `useGraphPreview`, apart from `head`, so the saved path only follows moves the store made; don't call `setHeadLocal` from it. The window keeps the undo rule and the store keeps the file (#568): move the rule into the store only for a client that does not run this UI, two tabs or users on one project, an agent tool that undoes along the path, or another head-desync bug. A compaction deletes nodes the path can name, so `useSession.forgetRemoved` drops them when `compact_session` ends, and undo/redo skip, rather than retry, a step the store refuses for a node its `get_graph` list no longer has (#595).
- The path survives a restart (#453): `useSession` saves it with the project (`save_head_trail` -> `.audiograph/trail.json`, `crates/session/src/trail.rs`) after every move, and reads it back (`get_head_trail`) at launch and in `restoreView`, where `resetHead(head, saved)` takes it only if it ends at the head the project opened on. The save goes through `lib/trailWriter.ts`, never through `inOrder`: one in flight, the newest replaces any waiting, and no edit waits for the disk. A missing or corrupt file is an empty path and never blocks opening a project. A new head-moving path must keep to `setHeadLocal` / `resetHead` so the file stays in step.
- Audio the project writes under a name made from its samples is named by `tools::provenance::audio_hash` (rate, channel count, then the samples) whichever writer wrote it: a destructive edit's output, a `load` copy, a clipboard blob, `generate_tone`, `generate_noise` (#620). `mix_to_new_track` is named by the blake3 of its WAV, header included, which holds the layout too. A file under a name is reused, not written, so a name that leaves the layout out hands one buffer another's file; name new audio through `audio_hash` only (`tests/audio_names_cover_layout.rs` fails a tool source that calls blake3 itself). Edits and `load` copies share `.audiograph/derived/`, so an edit that reproduces a `load` copy names its file, which is right and which compaction and the sweeps allow for by asking which nodes name a path. Projects written before #620 named edit outputs and generated audio by the blake3 of the samples alone (`provenance::legacy_sample_hash`). Nothing is renamed, and names are compared, never recomputed from a file (it holds 16-bit PCM, not the samples as hashed): a replay (`rederive`, the history sweep's `Verifier`) counts the older name as a match for what it wrote and rebuilds under the recorded one, learning it from the clip's `content_hash`, which an edit therefore keeps as the blake3 of its samples alone. `tests/legacy_audio_names.rs` builds such a project; keep the older-name match for as long as one can exist, and add no scheme field to stored ops for it.
- A lane control the user has set (gain or pan slider, mute, solo) is the user's until the session confirms it (#596). `Timeline` copies whatever `tracks` it is handed into its lanes, so a track-list read requested before the user's next input and landing after it used to put the older value back: a flicker, or a lost key tap, since the key-up then committed the value the session already held and `commitSlider` sent nothing. `lib/ownedControls.ts` holds the value from the slider's input event (the click, for a button) until a list read after the commit was answered has landed (`refreshTracks` numbers its reads and calls `owned.applied`, in the batch that sets the list), and `App` lays it over the list it hands the `Timeline` (`laneTracks`, memoised). A new lane control that shows its value ahead of its commit goes through it: `set` on input, a `claim` from `claimFor` passed to `commitTrackChange`. Anything that moves the session by itself (undo, redo, Set as head, A/B compare's Accept B, opening a project, and the assistant's edits, `agent://node-created`) calls `owned.clear()` before it re-reads the tracks; nothing else re-reads them on a head move, so a move that skips it leaves the lanes on the old list with the user's values over it (Accept B did, and the assistant's edits left a slider the user had moved and not let go of on the user's value). A refused commit is handed back like any other, with the session's value; a failed read confirms nothing, so the next read does. `App.laneControls.test.tsx` pins it in jsdom (undo, opening a project) and `e2e/lane-readback.spec.ts` with real key events; `App.sessionMoves.test.tsx` pins Accept B and the assistant's edits, and `e2e/accept-b.spec.ts` Accept B in Chromium.
- The mix the window plays is held in the preview cache (#607, #635). The transport loads its file again whenever the timeline mounts (a switch to the Graph or Transcript tab and back), and an entry the agent's renders, an audition or a compare had evicted meanwhile was a "Could not load the mix". So the window's `render_preview` command (Play, Preview and a graph preview) holds the entry it returns in `AppState::window_mix` (`window_mix.rs`, a `tools::preview_cache::Held`): the next `render_preview` replaces the hold, a project change releases it, a render that fails changes nothing, and the agent's tools render into the same cache with no hold of their own. A held entry is outside the cap, so `previews/` is bounded by the cap plus the A/B compare's pair (`compare.rs`, #575) plus this one mix. A mix gone anyway (a cache cleared by hand) is rendered again by the timeline that finds it missing, once for each path (`Timeline.mixMissing.test.tsx`, `e2e/mix-evicted.spec.ts`). The slot's lock is taken alone, and the hold a replace or release hands back is dropped after unlocking it, because dropping a hold evicts (`release_window_mix` below).
- Never replay a `thinking` / `redacted_thinking` block across a rebuilt `system` or `tools`, or after an earlier message is edited or removed: on Anthropic's 5.x models the signature binds to the whole prefix (`system`, `tools` and every message before the block), and a changed one is a 400 (#468). `run_turn` rebuilds `system` and `tools` every turn, so `strip_thinking` drops all earlier thinking at the start of each turn; only the current turn's blocks go back with its tool results. Anything that changes `system` or `tools` between a turn's steps has to strip there too, and so does editing or removing an earlier message mid-turn, which invalidates every block after it (client-side compaction, trimming old tool results, rewriting a stored `tool_use` or `tool_result`; Anthropic's server-side compaction and context editing are documented as valid, since the check compares the conversation as it was sent, <https://platform.claude.com/docs/en/build-with-claude/preserved-thinking>). Ollama's slim tool set and its names line (`tool_selection.rs`) change both from message to message, but are worked out once per turn, after the strip and before the first step, so they sit inside this rule. `tests/prior_turn_thinking.rs` pins it; `tests/live_thinking_binding.rs` (`#[ignore]`, `ANTHROPIC_E2E_KEY`) checks the real API.

## CI / release

- `ci.yml` runs on push to main + PRs: fmt, clippy, cargo test, frontend build (whose `tsc -b` type-checks the app, its tests and `vite.config.ts`), vitest, and a separate `e2e (chromium)` job — Playwright against a production build of the frontend, Linux only — and a `website (test)` job (the site's vitest suite and `pnpm typecheck`; it does not run `next build`). Tauri bundle is intentionally NOT in CI (too slow); release workflows cover that.
- `auto-release.yml` fires off CI's `workflow_run` on main: tags `v<version>-dev.<run_number>` (e.g. `v0.3.0-dev.N`) and dispatches `release-dev.yml`.
- `audit.yml` (workflow `Audit`) runs `cargo audit` on `Cargo.lock` weekly, on dispatch and on PRs that change `Cargo.lock` or a `Cargo.toml`; a vulnerability fails it, unmaintained/unsound/yanked crates only warn. It is a separate workflow, not a `ci.yml` job, so a new advisory can never fail the "CI" run `auto-release.yml` waits on. Clear a red one by bumping the crate (`cargo update -p <crate> --precise <version>`), never by adding an `ignore`; the `cargo-audit` version is pinned in the workflow's `CARGO_AUDIT_VERSION`.
- To cut a versioned release: bump the version in a `chore(release)` PR (all manifests, `Cargo.lock`, a changelog entry in `website/app/changelog/page.tsx`), merge it, then dispatch `release-dev.yml` with `tag=vX.Y.Z`, `channel=release` and the notes. Check the release is Latest, not a prerelease, and carries all six installers.
- `release-dev.yml` uses a `create-release` job + matrix to avoid the parallel-job race that produced duplicate releases for the same tag.
- Both release workflows ship the ONNX Runtime (#383): each leg runs `scripts/fetch-ml-runtime.sh` (and `scripts/installer-ml-runtime.py stage-vc-runtime` on Windows), builds with `--config src-tauri/tauri.ml-runtime.<os>.conf.json`, and runs `scripts/installer-ml-runtime.py check` on every installer before uploading it. Never put the runtime in `tauri.conf.json` itself: tauri-build fails on a resource that was not fetched. `release-dev.yml` gives tauri-action no `releaseId` (it would upload before the check) and uploads in its own step; `crates/tools/tests/release_ml_runtime.rs` pins all of this. To try a release build on a branch, dispatch `release-dev.yml` there with `dry_run: true`: it builds and checks, keeps the installers as a workflow artifact, and creates no tag or release.
- `release-dev.yml` has a `channel` dispatch input: `dev` (default — prerelease, not Latest, "unsigned dev build") and `release` (a real versioned release, not a prerelease, marked Latest). Tag pushes are always `dev`; a bare `vX.Y.Z` tag deliberately does not trigger it, so `release-signed.yml` owns those tags once certs exist. Both channels emit the same install warnings, because those describe the artifact rather than the channel.
- Signed releases (`release-signed.yml`) are manual `workflow_dispatch` and require Apple/Windows signing secrets. Same `create-release` + matrix + `publish` shape as `release-dev.yml`. tauri-action is given neither `tagName` nor `releaseId` there — it only builds, and upload happens after signing, so unsigned artifacts can never reach the release.
- Bundle targets are explicit in `tauri.conf.json`: `["app", "dmg", "msi", "nsis", "deb", "appimage"]`. Don't revert to `"all"` — it silently dropped installer formats under some build conditions.

## Audio engine / WaveSurfer quirks

- Playback runs in the webview: WaveSurfer plays the rendered preview mix through an HTML media element (WebKitGTK's GStreamer on Linux). There is no native playback path — #388 removed the unused `audio-io` crate and `play_state`; the only native audio I/O is microphone capture in `crates/recorder` (cpal input).

- In the packaged app `window.confirm` is async (tauri-plugin-dialog's init script), so `if (!window.confirm(...)) return;` never returns and Cancel is ignored (#544). Always `if (!(await confirmAction(...))) return;` (`src/lib/confirmAction.ts`): it asks the plugin's `confirm()` inside Tauri and awaits `window.confirm` elsewhere, because in 2.7.x the swapped-in `confirm` asks for a `plugin:dialog|confirm` command the crate no longer registers. `window.prompt` is not polyfilled and macOS webviews return null, so the app asks for text in a box in the page (the label lane's name box, which the ruler's add-marker opens too, #548) and `noWindowPrompt.test.ts` fails a call to it.
- A stored effect the renderer cannot run (a kind that is not streamable yet, or one it does not know) never fails a render (#520, #531): `effect_chain::build` leaves it out as it does a bypassed one, and `skipped_effects` / `audio_engine::render_warnings` list it from the stored chains with no render. `RenderReport.warnings` carries the list, the render tools put it in a `warnings` array, and the window shows it (`get_render_warnings`, `RenderWarningsNotice`, #542). Only `gain`, `limiter` and the three filters stream; `add_effect` refuses the rest. A new path that renders has to report them too: leaving an effect out unannounced is the silent wrong output the old fail-the-render rule existed to prevent.
- `wsRef.current.zoom()` throws "No audio loaded" when WaveSurfer has no decoded data — always guard with `if (!wsRef.current || duration === 0) return` and include `duration` in the useEffect dep array.
- React's `onWheel` is passive in Chromium/Tauri — Ctrl+scroll requires `el.addEventListener("wheel", handler, { passive: false })` via useEffect, not the `onWheel` JSX prop.
- Window-level `keydown` listeners do NOT stop each other via `e.stopPropagation()` — guard with a state variable (e.g., `!showShortcuts`) instead.
- Keyboard shortcut handlers in App.tsx that should fire without audio must be placed **before** `if (!timelineRef.current) return`, not after.

## Tauri command conventions

- Return type alias: `CmdResult<T>` (= `Result<T, String>`) — all commands use it; never raw `Result<T, String>`.
- Store and engine locks must be in separate scopes: acquire and drop store lock before opening engine lock to avoid double-borrow panics. Use `let state = { let store = lock_std(...); store.get(id)? };` pattern.
- Agent tools run off the store lock when `Tool::runs_off_the_lock()` is true (#421): `tools::Shared::dispatch` runs them on a `Store::stage()` handle and commits only if the head is unchanged. A lost race re-runs the tool on the new head, at most one re-run (two off-lock runs in all), and if both lose, a third run is made under the locks. A re-run is refused, with a `ToolResult::Error` for the model, when the user's edit changed a track the call names by position (a removal, or an undo that brings one back) or that track's clips, because the arguments no longer describe the session. The default is false, and `crates/tools/tests/off_lock_tools.rs` pins the list, so opting a tool in is a reviewed change.
- Lock order for the agent's dispatch: the dispatcher lock is taken alone, only to admit the call, and dropped before any other lock is taken, so do not wait on another lock while holding it there. `refresh_dispatcher_for_server` (`mcp_tool.rs`) does hold the dispatcher while it takes the MCP registry's lock; dispatcher then registry is the order in use, so do not add the reverse (the registry's lock held while asking for the dispatcher).
- The plan gate is one `ai::PlanGate` (`crates/ai/src/plan_gate.rs`, ADR 0002): a `tokio::sync::oneshot` per card, with the sender in the gate's slot. `Agent`, `AppState` and the CLI each hold a clone of the one handle; `Agent::new` and `run_turn` take it in place of the old `Notify`, revision slot and rejection flag, and `AppState` has no `plan_gate_open` or reset after the turn. `approval::ask` opens the question *before* it emits the card (`gate.ask()`), then awaits the `Waiting` for five minutes; `approve_plan` and `reject_plan` answer with `state.plan_gate.answer(..)`, which never takes the agent's lock (`send_message` holds it across the whole turn, so an answer that waited on it would deadlock; `answering_does_not_take_the_agents_lock` pins it) and needs no runtime. An answer takes the sender out of the slot, so a second click, a click with no card open and a click after a timeout all do nothing (#251): do not add a flag, a `Notify` or a reset to cover them. A dropped `Waiting` (timeout, a failed or cancelled turn) clears the slot itself. The gate's own lock is a leaf: nothing is taken while it is held. What a revision says is the desktop's (`revision_text`, `run_answer`); the gate carries the text untouched.
- One live `Store` per project folder (#501, #534, #566): the registry is in `session` (`crates/session/src/live.rs`, `Registry::global()`), not in the desktop crate. It maps a folder's identity (device and inode on unix, volume serial number and 128-bit file id on Windows: `FolderId`, never a path, so two spellings through a case-insensitive disk or a bind mount are one folder) to a weak handle, and the in-flight count `Store::staged_in_flight` reads is keyed by the same identity. The first store on a folder keeps a handle on it open for as long as any store lives, so the identity is not reused by a new folder (that handle means an open project's volume cannot be ejected, and a folder that cannot be opened for reading cannot be opened as a project). Each store registers the canonical path it reads its folder through and keeps it while it lives (it changes when the folder is renamed and the store is read again through the new name with `reread_into`; a staged edit keeps the one it started with): a write open of a path that a live store of a *different* folder writes through (a project restored over itself, or trashed and made again) fails with `Error::FolderReplaced` until that store is gone, because it writes by path into the new folder; `open_project_with` lets go of the window's handle and the idle agent's when nothing else holds the old store (`release_replaced_project`), and otherwise the user is told to wait for the assistant's turn to end. The opens are `Store::open_shared` (the project the window has, the agent works in and every command reaches: finds or builds-and-registers the one `LiveStore`; `open_shared_status` also says whether it was new), `Store::open_private` (a folder of the code's own, such as `batch_apply`'s per-file projects: `Error::AlreadyOpen` if the folder has a live store, and it holds a claim so the folder cannot be opened shared while it lives), `Store::open_read_only` (a reader that refuses every write with `Error::ReadOnly`; the reclaimer's planner) and the raw `Store::open`, which asks nothing and registers nothing and is for a folder only the caller can reach, so only tests call it. What keeps it out of shipped code is two things, neither the whole: the `raw-open` feature of `session` (the raw open exists only in session's test build and with that feature, and the crates that use it in tests enable it in `[dev-dependencies]` only, so a plain `cargo build`/`cargo check` of a crate that calls it fails to compile) and `crates/session/tests/no_unregistered_open.rs` (which lexes every crate's and app's source and fails on a raw open outside `#[cfg(test)]` items, brace-matched). The feature alone does not fail CI, because `cargo test` and `cargo clippy --all-targets` build the dev-dependency and Cargo unifies its features into the crate's non-test code; the test is what fails there, and a release build is where the feature fails. `AppState::set_open_project` takes a `LiveStore`, whose field is private to `session::live`, so a store the registry did not make cannot become the open project (a `compile_fail` doctest on `LiveStore`). `open_project_with` opens shared and, for a store that was already alive, reads the folder into it with `Store::reread_into` (in place, under the lock; a function returning a second `Store` on the live folder does not exist), so opening A, B, A during a turn on A gives the window the store the turn holds, not a second writer, and the unreferenced-file sweep runs under the lock tools stage with. The registry's lock is a leaf: nothing is taken while it is held, no store is dropped under it, and it may itself be taken while a store or engine lock is held (`batch_apply` and `tools::rederive` open folders of their own from inside a tool that holds the project's store), which cannot deadlock because the registry never waits for anything under its lock. `release_replaced_project` is the one path that holds a store's lock across the window's slots, and takes its locks in this order: the agent's (`try_lock_owned`) -> the registry (alone) -> the old store's (`try_lock`, held until the window has let go) -> the `store` slot -> `project_dir`, and then, with all of those let go, the window-mix lock (`release_window_mix`, taken alone, as in `set_open_project`). Nothing reverses it: the agent's lock comes before the slot everywhere, and no path locks a store while holding the slot. A test that needs two paths to be one folder builds a `Registry::with_identity(..)` (like the raw open, only in a test build or with `raw-open`) with an identity double instead of a bind mount.

## Website (`website/`)

- Separate Next.js 16 app, deliberately **outside** the pnpm workspace (so Vercel builds it standalone), with its own lockfile. The package is `edytlab-website`, so `pnpm --filter` does not reach it: `cd website && pnpm install --ignore-workspace`, then `pnpm test`, `pnpm typecheck`, `pnpm build`. `pnpm lint` calls `next lint`, which Next 16 removed — use `npx eslint .`.
- Animation is GSAP (`gsap`, `@gsap/react`); framer-motion is not installed. Components that animate need the `"use client"` directive, must respect `prefers-reduced-motion`, and must render their content visible without JavaScript.
- Demo videos: `website/lib/demos.ts` lists them, the files live in `website/public/demos/` (`<slug>.mp4` + `<slug>.jpg`), and `lib/demos.test.ts` fails if the list and the folder drift.
- Launch video and reels (`/videos`): `website/lib/videos.ts` lists them, and the files in `website/public/videos/` (`<slug>.mp4` + `<slug>.jpg`, plus `<slug>.vtt` for a 16:9 video's captions) are **copies** of the plain cuts under `marketing/` (the launch video, the reels, and the v0.7.0 promo's 16:9 and 9:16 cuts in `marketing/promo-v0.7.0/out/`; never a `*-narrated*` file, `audio/`, `sfx/`, `archive/` or the 1:1 cut: those carry ElevenLabs free-plan audio or repeat another cut). `lib/videos.test.ts` fails if a copy is not byte-identical (SHA-256) to its source, if the list and the folder drift, or if a `seconds`, `width` or `height` is not the file's own header; a re-cut in `marketing/` has to be copied over, its `.srt` converted (`lib/srt-to-vtt.ts`), its poster retaken (`posterAt`) and its `moments` (what happens, in order) brought in line with its cue file or `.srt`, which the test also holds. Each video has a page of its own, `/videos/<slug>`, where it is the one video on the page (Google indexes a video only when it is the main content of its page); `/videos` is a hub with no player, and a new video needs a `PAGE_UPDATED` date for its page.
- `crates/tools/tests/website_tool_docs.rs` checks tool names and counts in the site copy, so a tool rename or a new tool needs the site updated in the same PR.
- Vercel deploys only `main` and branches with `website` in their name (`website/vercel.json` → `git.deploymentEnabled`, pinned by `lib/vercelConfig.test.ts`). The Hobby plan allows 100 deployments a day and counts every one Vercel creates, including those the `ignoreCommand` cancels, so app-only branches must not create any. Put `website` in the name of a branch that changes `website/` to get a preview. CI's `website (test)` job only tests and type-checks the site, so run `pnpm build` in `website/` yourself before merging a site change.

## Acceptance gates

Before merging anything:
- `cargo fmt --all -- --check` clean
- `cargo clippy --workspace --all-targets -- -D warnings` clean
- `cargo test --workspace` passes
- `pnpm --filter @edytlab/desktop test` passes
- `pnpm --filter @edytlab/desktop test:slow-scheduler` passes — the same suite with React's scheduler 40 ms late (#349). A failure here that `test` does not show is a test asserting on async React state without waiting for it: wait on the state under test, or hold the backend's answer with `src/__tests__/held.ts`.
- `pnpm --filter @edytlab/desktop typecheck` clean — `tsc -b` over three programs: the app (no Node types, because it runs in a webview — #336), its tests (Node types, because vitest runs them in Node) and `vite.config.ts`. **Not** bare `tsc --noEmit`: the root `tsconfig.json` is a solution file with no inputs of its own, so that checks nothing and exits 0.
- `pnpm --filter @edytlab/desktop typecheck:e2e` clean
- Website changes: `pnpm test`, `pnpm typecheck` and `pnpm build` inside `website/` (see above).
- `pnpm --filter @edytlab/desktop test:e2e` passes — for anything that changes what mounts, draws, scrolls or decodes. jsdom cannot see those; `apps/desktop/e2e/` runs the real frontend in Chromium with only the IPC boundary replaced. Its fake backend answers from the Rust source (`e2e/backend.ts`), so a new command the app calls needs an answer there, taken from the command's own body.

**Every day, before stopping:**
