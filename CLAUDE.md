# CLAUDE.md

Project-level instructions for Claude Code sessions in this repository. These persist across sessions; treat them as durable user preferences.

## Workflow

### Pull requests

- **Always squash-merge a PR you opened once its CI is green.** Don't wait for explicit approval each time. If CI fails, investigate the failure rather than merging anyway.
- Open PRs as **drafts** by default; flip to ready when CI passes (squash-merge implies ready).
- One concern per PR. If a follow-up touches different files / different reviewer focus, open a separate PR rather than tacking it onto the current one.
- Reply to AI review comments (Gemini etc.) only when the suggestion is being declined or when noting a fix landed in a specific commit. Skip routine "fixed it" replies on threads that are already self-evident.

### Branches

- Feature branches: `claude/feature/<short-kebab-summary>`
- Fix branches: `claude/fix/<short-kebab-summary>`
- Docs and chores: `claude/docs/<…>`, `claude/chore/<…>` (a release bump is `claude/chore/release-<version>`).
- Always branch off latest `origin/main`, not whatever the working tree happens to be on.

### Commits

- Conventional-commit prefixes: `feat:`, `fix:`, `ci:`, `chore:`, `docs:`, `test:`, `refactor:`. Scope optional (`feat(ai): ...`).
- Each commit message ends with the session footer:
  ```
  https://claude.ai/code/session_<id>
  ```
  where `<id>` is the current session id (substituted by the harness at write time).

### Research

- Browse the web freely for any research: library and API docs, platform behaviour, prior art, model pricing, bug reports upstream. Prefer primary sources (official docs, specs, source code, release notes) and cite the URLs in the PR or issue that relies on them.

## Repo specifics

- Tauri 2 desktop app under `apps/desktop/`. Frontend in `apps/desktop/src/`, Rust backend in `apps/desktop/src-tauri/`.
- Workspace crates under `crates/`: `ai` (LLM provider abstraction and agent loop), `tools` (the agent's audio editing tools — `docs/tools-reference.md` is generated from them), `audio-engine` (render), `audio-time` (phase vocoder), `session` (the node graph), others.
- Multi-provider LLM support: Anthropic, OpenRouter, OpenAI, Groq, Gemini and Ollama (local, no key). The `LlmProvider` trait in `crates/ai/src/provider.rs` is the extension point — request serialization + SSE parsing are per-provider. So is how much of the tool list a request carries (`tool_set()`): Ollama sends `ToolSet::Slim` (`crates/ai/src/tool_selection.rs`: a core list plus the tools the message names, the assistant just proposed or the user named earlier, compacted, within a byte budget, picked once per turn, with the names of the rest in one line of the system prompt so the model knows they exist); every other provider sends all permitted tools, and Anthropic must, for its prompt cache. `crates/ai/tests/request_size.rs` bounds the slim request and ratchets the full one's system and tool sizes (`cargo test -p ai --test request_size -- --nocapture` prints them).
- Per-provider keychain slots: `<provider_id>_api_key`, `<provider_id>_model`, `<provider_id>_base_url`, `<provider_id>_effort`, plus an `active_provider` slot. Anthropic's slot is `anthropic_api_key`, the name builds before multi-provider used, so old keys are found with no migration. On Linux the store is the Secret Service (GNOME Keyring, KWallet or KeePassXC), with the kernel keyring as the fallback for the current boot only when none is running; `get_keychain_persistence` reports which applies and the app shows a banner (#394). `has_api_key` rejects when the keychain cannot be read — that is not the same as `false`. The commands that write a slot (`set_api_key`, `set_api_key_for`, `set_active_provider`, `set_base_url_for`, `set_effort_for`, `set_active_model`) answer with the same `{ persistent, reason }` for the save they made, so a service that went away after launch is not silent: Settings shows the banner's text (`lib/keychainNotice.ts`) and holds the dialog open on **Continue** (#539). After a startup the keychain refused (`AppState::keychain_refused`), `rebuild_agent_into` makes no keychain read and builds no agent until a key or provider save lifts the refusal; `send_message` says why.
- App version is canonical in `apps/desktop/src-tauri/tauri.conf.json` — the `package.json` files and Cargo's `[workspace.package] version` mirror it, and `appVersion.test.ts` fails if they drift.
- Demucs and Whisper (`crates/ml-*`) are wired in as tools but their inference is not shipped (#383–#385). Don't describe stem separation or transcription as working in docs or site copy. A verified, resumable model downloader (`ml_pipeline::fetched_model_path`) and the runtime gate below landed under #383, but nothing calls the downloader and no model is pinned, so nothing is downloaded. Don't write that the app "downloads" or "fetches" speech models either. Pieces that need no runtime have landed ahead of the inference: `ml-demucs` has `htdemucs`' STFT/iSTFT (`spec.rs`, #549) and the segment and overlap-add pipeline behind a `SegmentModel` trait (`separate.rs`, #550); `ml-whisper` has the log-mel spectrogram (`mel.rs`, #554), the token decoder (`tokenizer.rs`, #555), the greedy decoding loop behind a `DecoderStep` trait (`decode.rs`, #556) and word timing from cross-attention with DTW (`timing.rs`, #557). Each is checked against the reference implementation, and nothing calls any of them, so `separate_stems` and `transcribe` still return "not implemented in this build" and "ported" is not "working". `htdemucs` is the only Demucs model id (`SUPPORTED_MODEL_IDS`, the `separate_stems` enum); `htdemucs_ft` and `DEMUCS_FT_MODEL_PATH` are gone (#547).
- Anything that builds an `ort` session calls `ml_pipeline::runtime::ensure()` first. With `load-dynamic`, `ort` 2.0.0-rc.13 returns an error from `ort::init_from` when it cannot load the ONNX Runtime library (rc.12 deadlocked there and in every other entry point), but its implicit load, which `Session::builder` and `ort::api()` do on first use, panics (a release build aborts, and tools run while the agent loop holds the store and engine locks), and a bare or relative path goes to the system loader's search instead of failing. `ensure()` finds the library by absolute path and checks it before `ort` sees it. It looks in `ORT_DYLIB_PATH`, then the bundle directory the app registers at startup (`runtime::set_bundle_dir`, once: `Contents/Frameworks` on macOS, Tauri's resource directory on Linux, none on Windows), then next to the executable; on macOS older than `min_macos` in `ml-runtime.json` it answers `RuntimeUnsupported` before opening the file. The `ml_runtime_status` command and the Settings line report what it found (`edytlab-desktop --ml-runtime-status` prints the same answer as JSON with no window). Every release installer after v0.6.1 carries ONNX Runtime 1.23.2 and its notices (and on Windows the four VC++ runtime DLLs it imports, `vc_runtime` in `ml-runtime.json`), so an installed build says bundled; a build from source has none and says not installed in this build. That carries no model and runs no inference.
- Undo/redo follow the path the user took (`apps/desktop/src/lib/headTrail.ts`, held by `useSession`), never `node.parent` alone. Node ids hash state only, so a revisited state keeps its first parent (#398). Every frontend head move must go through `setHeadLocal` (edits, agent, graph) or `resetHead` (opening a project). `GraphView` never calls `set_head_to` itself (Set as head goes through App's `onSetHead`), and anything showing session state re-reads on a `head` change, since `set_head_to` emits no event. A click on a graph bubble is a preview, not a head move (#522): it lives in `useGraphPreview`, apart from `head`, so the saved path only follows moves the store made; don't call `setHeadLocal` from it. The window keeps the undo rule and the store keeps the file (#568): move the rule into the store only for a client that does not run this UI, two tabs or users on one project, an agent tool that undoes along the path, or another head-desync bug. A compaction deletes nodes the path can name, so `useSession.forgetRemoved` drops them when `compact_session` ends, and undo/redo skip, rather than retry, a step the store refuses for a node its `get_graph` list no longer has (#595).
- The path survives a restart (#453): `useSession` saves it with the project (`save_head_trail` -> `.audiograph/trail.json`, `crates/session/src/trail.rs`) after every move, and reads it back (`get_head_trail`) at launch and in `restoreView`, where `resetHead(head, saved)` takes it only if it ends at the head the project opened on. The save goes through `lib/trailWriter.ts`, never through `inOrder`: one in flight, the newest replaces any waiting, and no edit waits for the disk. A missing or corrupt file is an empty path and never blocks opening a project. A new head-moving path must keep to `setHeadLocal` / `resetHead` so the file stays in step.
- Never replay a `thinking` / `redacted_thinking` block across a rebuilt `system` or `tools`, or after an earlier message is edited or removed: on Anthropic's 5.x models the signature binds to the whole prefix (`system`, `tools` and every message before the block), and a changed one is a 400 (#468). `run_turn` rebuilds `system` and `tools` every turn, so `strip_thinking` drops all earlier thinking at the start of each turn; only the current turn's blocks go back with its tool results. Anything that changes `system` or `tools` between a turn's steps has to strip there too, and so does editing or removing an earlier message mid-turn, which invalidates every block after it (client-side compaction, trimming old tool results, rewriting a stored `tool_use` or `tool_result`; Anthropic's server-side compaction and context editing are documented as valid, since the check compares the conversation as it was sent, <https://platform.claude.com/docs/en/build-with-claude/preserved-thinking>). Ollama's slim tool set and its names line (`tool_selection.rs`) change both from message to message, but are worked out once per turn, after the strip and before the first step, so they sit inside this rule. `tests/prior_turn_thinking.rs` pins it; `tests/live_thinking_binding.rs` (`#[ignore]`, `ANTHROPIC_E2E_KEY`) checks the real API.

## CI / release

- `ci.yml` runs on push to main + PRs: fmt, clippy, cargo test, frontend build (whose `tsc -b` type-checks the app, its tests and `vite.config.ts`), vitest, and a separate `e2e (chromium)` job — Playwright against a production build of the frontend, Linux only — and a `website (test)` job (the site's vitest suite and `pnpm typecheck`; it does not run `next build`). Tauri bundle is intentionally NOT in CI (too slow); release workflows cover that.
- `auto-release.yml` fires off CI's `workflow_run` on main: tags `v<version>-dev.<run_number>` (e.g. `v0.3.0-dev.N`) and dispatches `release-dev.yml`.
- `audit.yml` (workflow `Audit`) runs `cargo audit` on `Cargo.lock` weekly, on dispatch and on PRs that change `Cargo.lock` or a `Cargo.toml`; a vulnerability fails it, unmaintained/unsound/yanked crates only warn. It is a separate workflow, not a `ci.yml` job, so a new advisory can never fail the "CI" run `auto-release.yml` waits on. Clear a red one by bumping the crate (`cargo update -p <crate> --precise <version>`), never by adding an `ignore`; the `cargo-audit` version is pinned in the workflow's `CARGO_AUDIT_VERSION`.
- To cut a versioned release: bump the version in a `chore(release)` PR (all manifests, `Cargo.lock`, a changelog entry in `website/app/changelog/page.tsx`), merge it, then dispatch `release-dev.yml` with `tag=vX.Y.Z`, `channel=release` and the notes. Check the release is Latest, not a prerelease, and carries all six installers.
- `release-dev.yml` uses a `create-release` job + matrix to avoid the parallel-job race that produced duplicate releases for the same tag.
- Both release workflows ship the ONNX Runtime (#383): each leg runs `scripts/fetch-ml-runtime.sh` (and `scripts/installer-ml-runtime.py stage-vc-runtime` on Windows), builds with `--config src-tauri/tauri.ml-runtime.<os>.conf.json`, and runs `scripts/installer-ml-runtime.py check` on every installer before uploading it. Never put the runtime in `tauri.conf.json` itself: tauri-build fails on a resource that was not fetched. `release-dev.yml` gives tauri-action no `releaseId` (it would upload before the check) and uploads in its own step; `crates/tools/tests/release_ml_runtime.rs` pins all of this. To try a release build on a branch, dispatch `release-dev.yml` there with `dry_run: true`: it builds and checks, keeps the installers as a workflow artifact, and creates no tag or release.
- `release-dev.yml` has a `channel` dispatch input: `dev` (default — prerelease, not Latest, "unsigned dev build") and `release` (a real versioned release, not a prerelease, marked Latest). Tag pushes are always `dev`; a bare `vX.Y.Z` tag deliberately does not trigger it, so `release-signed.yml` owns those tags once certs exist. Both channels emit the same install warnings, because those describe the artifact rather than the channel.
- Signed releases (`release-signed.yml`) are manual `workflow_dispatch` and require Apple/Windows signing secrets. Same `create-release` + matrix + `publish` shape as `release-dev.yml`. tauri-action is given neither `tagName` nor `releaseId` there — it only builds, and upload happens after signing, so unsigned artifacts can never reach the release.
- Bundle targets are explicit in `tauri.conf.json`: `["app", "dmg", "msi", "nsis", "deb", "appimage"]`. Don't revert to `"all"` — it silently dropped installer formats under some build conditions.

## Audio engine / WaveSurfer quirks

- Playback runs in the webview: WaveSurfer plays the rendered preview mix through an HTML media element (WebKitGTK's GStreamer on Linux). There is no native playback path — #388 removed the unused `audio-io` crate and `play_state`; the only native audio I/O is microphone capture in `crates/recorder` (cpal input).

- In the packaged app `window.confirm` is async (tauri-plugin-dialog's init script), so `if (!window.confirm(...)) return;` never returns and Cancel is ignored (#544). Always `if (!(await confirmAction(...))) return;` (`src/lib/confirmAction.ts`): it asks the plugin's `confirm()` inside Tauri and awaits `window.confirm` elsewhere, because in 2.7.x the swapped-in `confirm` asks for a `plugin:dialog|confirm` command the crate no longer registers. `window.prompt` is not polyfilled and macOS webviews return null, so the app asks for text in a box in the page (the label lane's name box, which the ruler's add-marker opens too, #548) and `noWindowPrompt.test.ts` fails a call to it.
- A stored effect the renderer cannot run (a kind that is not streamable yet, or one it does not know) never fails a render (#520, #531): `effect_chain::build` leaves it out as it does a bypassed one, and `skipped_effects` / `audio_engine::render_warnings` list it from the stored chains with no render. `RenderReport.warnings` carries the list, the render tools put it in a `warnings` array, and the window shows it (`get_render_warnings`, `RenderWarningsNotice`, #542). Only `gain`, `limiter` and the three filters stream; `add_effect` refuses the rest. A new path that renders has to report them too: leaving an effect out unannounced is the silent wrong output the old fail-the-render rule existed to prevent.
- `wsRef.current.zoom()` throws "No audio loaded" when WaveSurfer has no decoded data — always guard with `if (!wsRef.current || duration === 0) return` and include `duration` in the useEffect dep array.
- React's `onWheel` is passive in Chromium/Tauri — Ctrl+scroll requires `el.addEventListener("wheel", handler, { passive: false })` via useEffect, not the `onWheel` JSX prop.
- Window-level `keydown` listeners do NOT stop each other via `e.stopPropagation()` — guard with a state variable (e.g., `!showShortcuts`) instead.
- Keyboard shortcut handlers in App.tsx that should fire without audio must be placed **before** `if (!timelineRef.current) return`, not after.

## Tauri command conventions

- Return type alias: `CmdResult<T>` (= `Result<T, String>`) — all commands use it; never raw `Result<T, String>`.
- Store and engine locks must be in separate scopes: acquire and drop store lock before opening engine lock to avoid double-borrow panics. Use `let state = { let store = lock_std(...); store.get(id)? };` pattern.
- Agent tools run off the store lock when `Tool::runs_off_the_lock()` is true (#421): `tools::Shared::dispatch` runs them on a `Store::stage()` handle and commits only if the head is unchanged. A lost race re-runs the tool on the new head, at most one re-run (two off-lock runs in all), and if both lose, a third run is made under the locks. A re-run is refused, with a `ToolResult::Error` for the model, when the user's edit changed a track the call names by position (a removal, or an undo that brings one back) or that track's clips, because the arguments no longer describe the session. The default is false, and `crates/tools/tests/off_lock_tools.rs` pins the list, so opting a tool in is a reviewed change.
- Lock order for the agent's dispatch: the dispatcher lock is taken alone, only to admit the call, and dropped before any other lock is taken, so do not wait on another lock while holding it there. `refresh_dispatcher_for_server` (`mcp_tool.rs`) does hold the dispatcher while it takes the MCP registry's lock; dispatcher then registry is the order in use, so do not add the reverse (the registry's lock held while asking for the dispatcher).
- One live `Store` per project folder (#501, #534): `AppState::live_stores` (`live_stores.rs`) maps each canonical folder to a weak handle, and every `Store` that goes into `AppState` is registered there. `open_project_with` finds or builds-and-registers the store and re-reads the folder into it, so opening A, B, A during a turn on A gives the window the store the turn holds, not a second writer, and the unreferenced-file sweep runs under the lock tools stage with. Code that needs the open project's store takes it from `AppState` and does not `Store::open` the folder itself (the exceptions are the CLI, which is its own process, the scratch stores in `tools`, which are their own folders, and the reclaimer's read-only planner). The registry's lock is a leaf: taken alone for a lookup or an insert, never held with the store, engine, dispatcher, agent or `AppState` locks.

## Website (`website/`)

- Separate Next.js 16 app, deliberately **outside** the pnpm workspace (so Vercel builds it standalone), with its own lockfile. The package is `edytlab-website`, so `pnpm --filter` does not reach it: `cd website && pnpm install --ignore-workspace`, then `pnpm test`, `pnpm typecheck`, `pnpm build`. `pnpm lint` calls `next lint`, which Next 16 removed — use `npx eslint .`.
- Animation is GSAP (`gsap`, `@gsap/react`); framer-motion is not installed. Components that animate need the `"use client"` directive, must respect `prefers-reduced-motion`, and must render their content visible without JavaScript.
- Demo videos: `website/lib/demos.ts` lists them, the files live in `website/public/demos/` (`<slug>.mp4` + `<slug>.jpg`), and `lib/demos.test.ts` fails if the list and the folder drift.
- `crates/tools/tests/website_tool_docs.rs` checks tool names and counts in the site copy, so a tool rename or a new tool needs the site updated in the same PR.
- Vercel deploys only `main` and branches with `website` in their name (`website/vercel.json` → `git.deploymentEnabled`, pinned by `lib/vercelConfig.test.ts`). The Hobby plan allows 100 deployments a day and counts every one Vercel creates, including those the `ignoreCommand` cancels, so app-only branches must not create any. Put `website` in the name of a branch that changes `website/` to get a preview. CI's `website (test)` job only tests and type-checks the site, so run `pnpm build` in `website/` yourself before merging a site change.

## Acceptance gates

Before merging anything:
- `cargo fmt --all -- --check` clean
- `cargo clippy --workspace --all-targets -- -D warnings` clean
- `cargo test --workspace` passes
- `pnpm --filter @edytlab/desktop test` passes
- `pnpm --filter @edytlab/desktop test:slow-scheduler` passes — the same suite with React's scheduler 40 ms late (#349). A failure here that `test` does not show is a test asserting on async React state without waiting for it: wait on the state under test, or hold the backend's answer with `src/__tests__/held.ts`.
- `pnpm --filter @edytlab/desktop typecheck` clean — `tsc -b` over three programs: the app (no Node types, because it runs in a webview — #336), its tests (Node types, because vitest runs them in Node) and `vite.config.ts`. **Not** bare `tsc --noEmit`: the root `tsconfig.json` is a solution file with no inputs of its own, so that checks nothing and exits 0.
- `pnpm --filter @edytlab/desktop typecheck:e2e` clean
- Website changes: `pnpm test`, `pnpm typecheck` and `pnpm build` inside `website/` (see above).
- `pnpm --filter @edytlab/desktop test:e2e` passes — for anything that changes what mounts, draws, scrolls or decodes. jsdom cannot see those; `apps/desktop/e2e/` runs the real frontend in Chromium with only the IPC boundary replaced. Its fake backend answers from the Rust source (`e2e/backend.ts`), so a new command the app calls needs an answer there, taken from the command's own body.
