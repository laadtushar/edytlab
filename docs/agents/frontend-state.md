# Frontend state and webview quirks

Read before touching undo/redo, the head trail, lane controls, the window's mix, WaveSurfer, keyboard or wheel handlers, or confirm/prompt dialogs.

## Undo, redo and the head trail

- Undo/redo follow the path the user took (`apps/desktop/src/lib/headTrail.ts`, held by `useSession`), never `node.parent` alone. Node ids hash state only, so a revisited state keeps its first parent (#398). Every frontend head move must go through `setHeadLocal` (edits, agent, graph) or `resetHead` (opening a project). `GraphView` never calls `set_head_to` itself (Set as head goes through App's `onSetHead`), and anything showing session state re-reads on a `head` change, since `set_head_to` emits no event. The History graph reads again on `useSession`'s one `graphVersion` (#602): a head move or a project opening, `agent://done` (a `name_node` label moves no head), and every `forgetRemoved` (a compaction ending, a refused undo). `GraphView` gets it as `refreshKey` and reads nowhere else but its own rename; a preview click is none of these. A click on a graph bubble is a preview, not a head move (#522): it lives in `useGraphPreview`, apart from `head`, so the saved path only follows moves the store made; don't call `setHeadLocal` from it. The window keeps the undo rule and the store keeps the file (#568): move the rule into the store only for a client that does not run this UI, two tabs or users on one project, an agent tool that undoes along the path, or another head-desync bug. A compaction deletes nodes the path can name, so `useSession.forgetRemoved` drops them when `compact_session` ends, and undo/redo skip, rather than retry, a step the store refuses for a node its `get_graph` list no longer has (#595).
- The path survives a restart (#453): `useSession` saves it with the project (`save_head_trail` -> `.audiograph/trail.json`, `crates/session/src/trail.rs`) after every move, and reads it back (`get_head_trail`) at launch and in `restoreView`, where `resetHead(head, saved)` takes it only if it ends at the head the project opened on. The save goes through `lib/trailWriter.ts`, never through `inOrder`: one in flight, the newest replaces any waiting, and no edit waits for the disk. A missing or corrupt file is an empty path and never blocks opening a project. A new head-moving path must keep to `setHeadLocal` / `resetHead` so the file stays in step.

## Lane controls

- A lane control the user has set (gain or pan slider, mute, solo) is the user's until the session confirms it (#596). `Timeline` copies whatever `tracks` it is handed into its lanes, so a track-list read requested before the user's next input and landing after it used to put the older value back: a flicker, or a lost key tap, since the key-up then committed the value the session already held and `commitSlider` sent nothing. `lib/ownedControls.ts` holds the value from the slider's input event (the click, for a button) until a successful list read after the commit was answered is adopted. `useSession.refreshTracks` owns numbered reads through its private track query and calls `owned.applied` in a layout effect only after the observer adopts the current snapshot; failed, cancelled or obsolete reads confirm nothing. `App` still owns control input and lays the held values over the list it hands the `Timeline` (`laneTracks`, memoised). A new lane control that shows its value ahead of its commit goes through it: `set` on input, a `claim` from `claimFor` passed to `commitTrackChange`, and `useSession({ trackControls: owned })` to confirm that owner's claims. Anything that moves the session by itself (undo, redo, Set as head, A/B compare's Accept B, opening a project, and the assistant's edits, `agent://node-created`) calls `owned.clear()` before it re-reads the tracks; nothing else re-reads them on a head move, so a move that skips it leaves the lanes on the old list with the user's values over it (Accept B did, and the assistant's edits left a slider the user had moved and not let go of on the user's value). A refused commit is handed back like any other, with the session's value. ADR 0001 is partially built through Stage 2: the provider and track query are present; Stage 3/4's mutation queue, ownership replacement, import guard and other queries remain pending, so keep `sessionQueue`, `OwnedControls`, the regex guards and `graphVersion`. `App.laneControls.test.tsx` pins it in jsdom (undo, opening a project) and `e2e/lane-readback.spec.ts` with real key events; `App.sessionMoves.test.tsx` pins Accept B and the assistant's edits, and `e2e/accept-b.spec.ts` Accept B in Chromium.

## The window's mix

- The mix the window plays is held in the preview cache (#607, #635). The transport loads its file again whenever the timeline mounts (a switch to the Graph or Transcript tab and back), and an entry the agent's renders, an audition or a compare had evicted meanwhile was a "Could not load the mix". So the window's `render_preview` command (Play, Preview and a graph preview) holds the entry it returns in `AppState::window_mix` (`window_mix.rs`, a `tools::preview_cache::Held`): the next `render_preview` replaces the hold, a project change releases it, a render that fails changes nothing, and the agent's tools render into the same cache with no hold of their own. A held entry is outside the cap, so `previews/` is bounded by the cap plus the A/B compare's pair (`compare.rs`, #575) plus this one mix. A mix gone anyway (a cache cleared by hand) is rendered again by the timeline that finds it missing, once for each path (`Timeline.mixMissing.test.tsx`, `e2e/mix-evicted.spec.ts`). The slot's lock is taken alone, and the hold a replace or release hands back is dropped after unlocking it, because dropping a hold evicts (`release_window_mix` in "One live Store per project folder", `docs/agents/tauri-conventions.md`).

## Dialogs

- In the packaged app `window.confirm` is async (tauri-plugin-dialog's init script), so `if (!window.confirm(...)) return;` never returns and Cancel is ignored (#544). Always `if (!(await confirmAction(...))) return;` (`src/lib/confirmAction.ts`): it asks the plugin's `confirm()` inside Tauri and awaits `window.confirm` elsewhere, because in 2.7.x the swapped-in `confirm` asks for a `plugin:dialog|confirm` command the crate no longer registers. `window.prompt` is not polyfilled and macOS webviews return null, so the app asks for text in a box in the page (the label lane's name box, which the ruler's add-marker opens too, #548) and `noWindowPrompt.test.ts` fails a call to it.

## WaveSurfer, React and keyboard quirks

- `wsRef.current.zoom()` throws "No audio loaded" when WaveSurfer has no decoded data — always guard with `if (!wsRef.current || duration === 0) return` and include `duration` in the useEffect dep array.
- React's `onWheel` is passive in Chromium/Tauri — Ctrl+scroll requires `el.addEventListener("wheel", handler, { passive: false })` via useEffect, not the `onWheel` JSX prop.
- Window-level `keydown` listeners do NOT stop each other via `e.stopPropagation()` — guard with a state variable (e.g., `!showShortcuts`) instead.
- Keyboard shortcut handlers in App.tsx that should fire without audio must be placed **before** `if (!timelineRef.current) return`, not after.
