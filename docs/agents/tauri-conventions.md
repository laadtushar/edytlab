# Tauri commands, locks and the agent loop

Read before adding, changing or documenting a Tauri command, taking a lock, touching the plan gate, opening a project's store, replaying thinking blocks, or changing bundled skills.

## Commands and locks

- Every command returns `CmdResult<T>` (= `Result<T, String>`), never a raw `Result<T, String>`.
- Store and engine locks must be in separate scopes: acquire and drop store lock before opening engine lock to avoid double-borrow panics. Use `let state = { let store = lock_std(...); store.get(id)? };` pattern.
- Lock order for the agent's dispatch: the dispatcher lock is taken alone, only to admit the call, and dropped before any other lock is taken, so do not wait on another lock while holding it there. `refresh_dispatcher_for_server` (`mcp_tool.rs`) does hold the dispatcher while it takes the MCP registry's lock; dispatcher then registry is the order in use, so do not add the reverse (the registry's lock held while asking for the dispatcher).

## Documenting a command

- Every command added or changed is documented in `docs/api-reference.md` and `website/lib/docs/api-data.ts` (the fake backend in `e2e/backend.ts` is already an acceptance gate). The site's API reference is one page per area, all made from that file (`/docs/api-reference/[area]`; a new area is an object in `apiAreas` plus a `PAGE_UPDATED` date, no page file), and lists every command, one row each, and so does the md. The data is guarded by `website/lib/apiReferencePage.test.ts` (each name in `generate_handler!` in `lib.rs`, camel-cased, has a row, and no row outlives its command); the md is checked against the bridge's exports by `apiReferenceCoverage.test.ts`, not against `lib.rs`. A changed return type or error is edited in both. The hand-written command count (compute it with `grep -c '#\[tauri::command' apps/desktop/src-tauri/src/commands.rs`) is not guarded: `docs/architecture.md` (the "~N commands" box), `docs/development-guide.md` ("~N of them") and `website/app/docs/developer-guide/page.tsx` all say about 110, which holds until the count passes 115 or drops below 105 (the recording-latency commands took it past 105, so all three copies moved to a new round number), and `docs/saas-evaluation.md` gives the exact count with its async and plain split and the line count of `commands.rs`, so it moves with every command.

## The plan gate

- The plan gate is one `ai::PlanGate` (`crates/ai/src/plan_gate.rs`, ADR 0002): a `tokio::sync::oneshot` per card, with the sender in the gate's slot. `Agent`, `AppState` and the CLI each hold a clone of the one handle; `Agent::new` and `run_turn` take it in place of the old `Notify`, revision slot and rejection flag, and `AppState` has no `plan_gate_open` or reset after the turn. `approval::ask` opens the question *before* it emits the card (`gate.ask()`), then awaits the `Waiting` for five minutes; `approve_plan` and `reject_plan` answer with `state.plan_gate.answer(..)`, which never takes the agent's lock (`send_message` holds it across the whole turn, so an answer that waited on it would deadlock; `answering_does_not_take_the_agents_lock` pins it) and needs no runtime. An answer takes the sender out of the slot, so a second click, a click with no card open and a click after a timeout all do nothing (#251): do not add a flag, a `Notify` or a reset to cover them. A dropped `Waiting` (timeout, a failed or cancelled turn) clears the slot itself. The gate's own lock is a leaf: nothing is taken while it is held. What a revision says is the desktop's (`revision_text`, `run_answer`); the gate carries the text untouched.

## One live Store per project folder

- One live `Store` per project folder (#501, #534, #566): the registry is in `session` (`crates/session/src/live.rs`, `Registry::global()`), not in the desktop crate. It maps a folder's identity (device and inode on unix, volume serial number and 128-bit file id on Windows: `FolderId`, never a path, so two spellings through a case-insensitive disk or a bind mount are one folder) to a weak handle, and the in-flight count `Store::staged_in_flight` reads is keyed by the same identity. The first store on a folder keeps a handle on it open for as long as any store lives, so the identity is not reused by a new folder (that handle means an open project's volume cannot be ejected, and a folder that cannot be opened for reading cannot be opened as a project). Each store registers the canonical path it reads its folder through and keeps it while it lives (it changes when the folder is renamed and the store is read again through the new name with `reread_into`; a staged edit keeps the one it started with): a write open of a path that a live store of a *different* folder writes through (a project restored over itself, or trashed and made again) fails with `Error::FolderReplaced` until that store is gone, because it writes by path into the new folder; `open_project_with` lets go of the window's handle and the idle agent's when nothing else holds the old store (`release_replaced_project`), and otherwise the user is told to wait for the assistant's turn to end. The opens are `Store::open_shared` (the project the window has, the agent works in and every command reaches: finds or builds-and-registers the one `LiveStore`; `open_shared_status` also says whether it was new), `Store::open_private` (a folder of the code's own, such as `batch_apply`'s per-file projects: `Error::AlreadyOpen` if the folder has a live store, and it holds a claim so the folder cannot be opened shared while it lives), `Store::open_read_only` (a reader that refuses every write with `Error::ReadOnly`; the reclaimer's planner) and the raw `Store::open`, which asks nothing and registers nothing and is for a folder only the caller can reach, so only tests call it. What keeps it out of shipped code is two things, neither the whole: the `raw-open` feature of `session` (the raw open exists only in session's test build and with that feature, and the crates that use it in tests enable it in `[dev-dependencies]` only, so a plain `cargo build`/`cargo check` of a crate that calls it fails to compile) and `crates/session/tests/no_unregistered_open.rs` (which lexes every crate's and app's source and fails on a raw open outside `#[cfg(test)]` items, brace-matched). The feature alone does not fail CI, because `cargo test` and `cargo clippy --all-targets` build the dev-dependency and Cargo unifies its features into the crate's non-test code; the test is what fails there, and a release build is where the feature fails. `AppState::set_open_project` takes a `LiveStore`, whose field is private to `session::live`, so a store the registry did not make cannot become the open project (a `compile_fail` doctest on `LiveStore`). `open_project_with` opens shared and, for a store that was already alive, reads the folder into it with `Store::reread_into` (in place, under the lock; a function returning a second `Store` on the live folder does not exist), so opening A, B, A during a turn on A gives the window the store the turn holds, not a second writer, and the unreferenced-file sweep runs under the lock tools stage with. The registry's lock is a leaf: nothing is taken while it is held, no store is dropped under it, and it may itself be taken while a store or engine lock is held (`batch_apply` and `tools::rederive` open folders of their own from inside a tool that holds the project's store), which cannot deadlock because the registry never waits for anything under its lock. `release_replaced_project` holds a store's lock across the window's slots, taking locks in this order: the agent's (`try_lock_owned`) -> the registry (alone) -> the old store's (`try_lock`, held until the window has let go) -> the `store` slot -> `project_dir`, and then, with all of those let go, the window-mix lock (`release_window_mix`, taken alone, as in `set_open_project`). `run_track_tool_at_project` takes the captured store then the `store` slot for the identity check, releases the slot before engine and dispatcher, and dispatches only to the captured store. Nothing reverses these orders: the agent's lock comes before the slot everywhere, and no path locks a store while holding the slot. A test that needs two paths to be one folder builds a `Registry::with_identity(..)` (like the raw open, only in a test build or with `raw-open`) with an identity double instead of a bind mount.

## Thinking blocks

- Never replay a `thinking` / `redacted_thinking` block across a rebuilt `system` or `tools`, or after an earlier message is edited or removed: on Anthropic's 5.x models the signature binds to the whole prefix (`system`, `tools` and every message before the block), and a changed one is a 400 (#468). The private `Conversation` in `crates/ai/src/conversation.rs` owns history and `invalidate_thinking`; the loop calls it at turn start before adding user text or selecting slim tools, and again wherever anything changes `system` or `tools` between a turn's steps (provider adaptation, such as the ChatGPT tool ladder, is one instance). Within a turn, preserve signed blocks and their unchanged prefix. Editing or removing an earlier message mid-turn has to invalidate thinking there too, since it breaks every later block (client-side compaction, trimming old tool results, rewriting a stored `tool_use` or `tool_result`; Anthropic's server-side compaction and context editing are documented as valid, since the check compares the conversation as it was sent, <https://platform.claude.com/docs/en/build-with-claude/preserved-thinking>). Ollama's slim tool set and its names line (`tool_selection.rs`) are worked out once per turn, after invalidation and before the first step. The `chatgpt` provider's Responses `reasoning` items follow the same rule: they are kept as `redacted_thinking` blocks (`replays_thinking()`), echoed in `input` within the turn without their `id`, and removed at the next turn start. If a held approval wait is dropped, `Conversation` completes its held, unexecuted calls in history; this is history cleanup, not native tool cancellation or generic panic recovery. `tests/prior_turn_thinking.rs` pins it for Anthropic and `tests/chatgpt_provider.rs` (`reasoning_is_echoed_within_a_turn_and_never_across_turns`) for ChatGPT; `tests/live_thinking_binding.rs` (`#[ignore]`, `ANTHROPIC_E2E_KEY`) checks the real API.

## Bundled skills

- Bundled skills (`apps/desktop/src-tauri/resources/skills/*.md`) are kept current in `~/.edytlab/skills/` by `bundled_skills.rs` (#574, #631), which the window runs at every launch (`install_bundled_skills`). `~/.edytlab/skills/.bundled.json` records the SHA-256 of the text it installed for each file: a file that still matches is replaced when the bundled text changes, an edited one is left alone and the new text is written beside it as `<name>.bundled.md` (the loader and the Skills editor skip that name), and a deleted one is not reinstalled. An install from before the manifest counts a file as unedited only if its text is listed in `pre_manifest_skills.json`, and that list is frozen: a new or changed bundled skill needs no entry, and adding one would make such an install take a later skill for one the user deleted (`the_pre_manifest_list_never_changes` fails; `node scripts/pre-manifest-skill-hashes.mjs --check` checks the file against the git history, which needs a full clone). To change a bundled skill, edit its file and nothing else.
