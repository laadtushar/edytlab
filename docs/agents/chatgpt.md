# ChatGPT plan provider

Read before touching the `chatgpt` provider, its sign-in, its commands or its Settings and Chat UI.

## The provider

- The `chatgpt` provider (#474; `crates/ai/src/chatgpt/provider.rs`, spec `docs/specs/2026-10-10-chatgpt-subscription-sign-in.md`) runs the agent on a ChatGPT Plus or Pro plan through Sign in with ChatGPT, a preview. It is in `SUPPORTED_PROVIDER_IDS`, the desktop has its commands (next section), Settings offers it with a card, and the site and privacy copy name it: the three tests that compare the registry with Settings and the site (`settings_provider_list.rs`, `settings_default_models.rs`, `website_provider_claims.rs`) carry a `NOT_OFFERED_YET` list, empty now; a provider registered before it is offered goes in that list and comes out when its card and copy land. The site calls the set "six API providers plus your ChatGPT plan" everywhere; keep that wording. It has no key and no base URL: `credential_kind()` is `ChatGptOAuth`, `LlmConfig.credential` is a `Credential::ChatGpt(session)` whose bearer comes from `ChatGptSession` for every request (`LlmConfig::send_with`, `credential.rs`: one renewal and resend on a 401, then the answer), and the bearer goes only to `api.openai.com` (and the session's own calls to `auth.openai.com`): the provider's `honours_base_url_override()` is `false`, a session is refused by any other provider's config, the model list and TEST (`models::list_chatgpt_models`, `validate::probe_chatgpt`) read the session and take no key or address, and `list_models_for` and `probe_provider_for` refuse the id. A key is refused for it too (`send_with` answers `session_ended` to `Credential::ApiKey`; `Credential::TestBearer` exists only in test builds), and the desktop builds an agent for it only while its session is signed in and refuses to save a key or an address for it, signed in or not (`set_api_key_for`, `set_base_url_for`), and the CLI refuses `--provider chatgpt` (it has no browser to open). So it has no `chatgpt_api_key` or `chatgpt_base_url` slot, and nothing may write one; its slots are `chatgpt_refresh_token` (the session's, `store::REFRESH_TOKEN_SLOT`, an entry of the `secrets` item), `chatgpt_model` and `active_provider`. The token and the API address stay in Rust: do not add a way for the webview to hold, send or choose either. Each failure on its route is a `PlanUsageError` (`Error::PlanUsage`; its `code()` is what the window switches on), reached through `LlmProvider::classify_failure` from both the HTTP body and `StreamEvent::Error` (whose `kind` and `param` the loop now passes on), and none is retried on another provider. The mode classifier is not called (`skips_classifier()`: each call spends the person's allowance; every message is `general`). The tools go down a ladder when the route answers 400 with a `param` naming them (`ToolRung`: all in the `edytlab` namespace, `ToolSet::Slim` in it, an `additional_tools` input item, flat functions; `LlmProvider::adapt_after_refusal`), never the same body twice, the thinking dropped at each step; the rung that worked stays on the provider. Only a real account (spec §4.10) can say where it stops. `request_size.rs` ratchets the Responses request (`RESPONSES_*`) and holds the slim one to Ollama's bound. A preview can change under this: `crates/ai/tests/chatgpt_provider.rs` pins the request, the renewal and each error against a mock, so a change shows up as one failing test.

## The sign-in in the desktop

- **The ChatGPT sign-in in the desktop (#474; `apps/desktop/src-tauri/src/chatgpt.rs`).** One `ChatGptSession` is opened at startup (`AppState::install_chatgpt`: `SessionConfig::new(app_config_dir)`, so `registration.json` is in `<app config dir>/chatgpt/`; it reads that file and nothing else), and its `RefreshTokenStore` is `KeychainTokenStore`, on the slot `chatgpt_refresh_token` through `ai::keychain`'s `try_load_chatgpt_refresh_token` / `save_` / `delete_` (the same plumbing as the keys: the Linux kernel-keyring fallback of #394 is remembered and reported as `tokenStorage.kind: kernel_keyring`, `persistent: false`; a token the keychain refuses stays in memory, `kind: memory`). After a startup the keychain refused (`keychain_refused`, #497) its **reads** make no keychain call and answer with the same note every other read gives (`state::keychain_refusal_note`), the startup restore (`restore_chatgpt_at_startup`, in the startup reads) is skipped, and the status is `unread`; a save and a delete, the user's own acts, are made. Six commands, none returning a token or a path: `chatgpt_status`, `chatgpt_sign_in(intent)` (`sign_in`, `enable_plan_usage`, `another_account`), `chatgpt_cancel_sign_in`, `chatgpt_sign_out`, `chatgpt_forget_registration` (G13: sign out, then forget the registered client; `ChatGptSession::forget_registration`; the old entry may remain in ChatGPT's settings and `notice` says so) and `chatgpt_take_pending_message`. The browser is opened from Rust with `tauri-plugin-opener`'s `open_url`, **never registered as a plugin**: the window has no opener command or permission, capabilities and the CSP are unchanged, and the URL is never logged or put in an error. Every status change is sent on `chatgpt://status` (`events::CHATGPT_STATUS`, deduplicated by `ChatGptHandle::publish`, called after each command, each turn, and the restore); the state is `signed_out`, `signing_in`, `signed_in`, `plan_disabled`, `session_ended` (+ reason code), `unread` or `unavailable`, with the email only when the session has one. The provider's refusals follow the session: `set_active_provider("chatgpt")`, `provider_is_configured` and `rebuild_agent_from` (profile pins included) require a signed-in session, and the agent is built with `LlmConfig::with_credential(provider, Credential::ChatGpt(session))`; `set_api_key_for` / `set_base_url_for` still refuse it. **The agent's `ChatGptProvider` is the agent's alone** (review finding 7 of #695): `ChatGptHandle::new_agent_provider` makes it, and Test (`test_api_key_for("chatgpt")`) and the model list (`list_models_for("chatgpt")`, and the read after a sign-in and on an agent build) each run on a copy made from what the app remembers (`list_models` / `probe`), never the agent's instance, so the ladder they step, the levels they read and the stream parser they restart cannot change a turn in flight. What a copy learns (a deeper rung, the models' `reasoning_levels`) is kept in `ChatGptHandle`'s memory on purpose and reaches the running agent only at `turn_boundary` (start of `send_message`, agent lock held), and the next agent built starts from it (`with_tool_rung` carries the rung across `rebuild_agent`; the rung the agent itself stepped to is read back at `end_of_turn` and when it is replaced); `account_changed` (sign-out, start over, another account) resets it all (`reset_adaptations`) and a catalogue read for the new account is kept. No local path reaches the window: `sign_in_error_text` gives fixed sentences for `SignInError::Lock` / `Registration` (the detail goes to the log) and every text the handle returns is scrubbed of the config folder (`Hooking::private_dir`); `provider_is_configured` / `has_api_key(_for)` reject, rather than answer `false`, for a saved sign-in that could not be read (`unread`, #394); `chatgpt_forget_registration` does not report `signing_in` while it runs (it holds the session's sign-in guard only to keep a sign-in from starting); the missing agent of a signed-out plan says to Continue with ChatGPT in Settings, not to set a key (`CommandError::NoAgentChatGpt`). `a_model_list_during_a_turn_does_not_change_that_turns_tools_or_reasoning_layout` pins it. A failed turn on the plan rejects `send_message` with text that starts `[plan-usage code=<PlanUsageError::code()> request-id=<id>] <sentence>` (`plan_usage_text`; parsed by `parsePlanUsageError` in `lib/chat-errors.ts`, which also keeps these out of the refused-key route). **G9:** on `session_ended` the turn's message is kept (`PendingMessage`, in memory only, `status.pendingMessage`, taken by `chatgpt_take_pending_message`), but only if the session *ended* (not signed out) and the **account generation** (`ChatGptHandle::account_generation`, moved by `account_changed`: sign-out, start over, another account) is still the one the turn began under (`keep_pending`), and `account_changed` clears it, so an in-flight turn cannot hand a message to the next account; the same generation stamps every copy (`fork`) so a copy that began for the old account teaches the new one nothing, and the running agent's provider restarts at the next `turn_boundary` when it is behind: if the turn got no further than sending it, it is withdrawn from the agent's conversation (`Agent::withdraw_unanswered_text`) so a resend is not joined onto its own copy and `resumeText` is the text; if tools had run, `resumeText` is `CONTINUE_TEXT`. The agent is not rebuilt by a sign-in (history stays) unless it was dropped. **The window** adds `open_chatgpt_usage` (a seventh command: it takes no argument and opens only the fixed `ai::chatgpt::errors::USAGE_URL` with the same Rust-side opener, so the window still has none; `openChatgptUsage` in the bridge) and the UI. `ProviderId` now includes `"chatgpt"`; `KeyProviderId` is every other provider and is what the key and address functions take. Settings → Account lists **ChatGPT plan** with the others, and choosing it shows `ChatGptCard` (`components/ChatGptCard.tsx`) in place of the key, address and model fields: signed out, signing in (with the G6 hint after 20 s), signed in (model picker from `list_models_for("chatgpt")`, saving the account's first model for a person who chose none, and an effort picker from the chosen model's `reasoning_levels`, hidden when none is offered, saved at once through `set_effort_for`), plan usage declined, session ended, unread, unavailable, and any state it does not know (a neutral "Working…"). Choosing the plan when signed out only shows the card; a sign-in the card starts makes it the active provider (`set_active_provider`, skipped when it already is, because that rebuilds the agent and drops its conversation). Copy is in `lib/chatgptCopy.ts`; the storage banner reuses `keychainNotice.ts` (`chatGptStorageNotice`). In Chat a failed plan turn draws a card by code (`components/PlanUsageCards.tsx`): `usage_limit` (no retry, no fallback, Manage usage, request ID with copy, Copy request for admin), `session_ended` (Continue: `chatgptSignIn("sign_in")`, `chatgptTakePendingMessage()`, then `sendMessage(resumeText, disabledTools)` without a second copy in the log) and one sentence plus the request ID for the rest. The backend folds the workplace usage-limit code into `usage_limit`, so Copy request for admin is on every usage-limit card. The privacy and site copy say that sign-in adds requests to `auth.openai.com` and `api.openai.com` (the "A new outbound network request" trigger of the Staleness sweep in `CLAUDE.md`).
