## CI

- `ci.yml` runs on push to main + PRs. Check names (keep them stable: branch rules and `auto-release.yml` name them): `build (linux-x86_64)`, `build (macos-arm64)`, `build (windows-x86_64)`, `frontend (test)`, `e2e (chromium)`, `website (test)`, plus `changes`. Each `build` leg runs clippy and `cargo nextest run --workspace --profile ci` (`.config/nextest.toml`; a process per test, so no `--test-threads=1`) and `cargo test --doc` (nextest runs no doctests); `cargo fmt --check` and the Linux-only ONNX Runtime smoke run on the Linux leg. The frontend (vitest, slow-scheduler vitest, `tsc -b` + vite build) is its own `frontend (test)` job on Linux, not part of `build`. `e2e (chromium)` is Playwright against a production build of the frontend, Linux only; `website (test)` is the site's vitest suite and `pnpm typecheck` (it does not run `next build`). CI sets `CARGO_PROFILE_DEV_DEBUG=0` and `CARGO_PROFILE_TEST_DEBUG=0`. On Windows `target/` is a Dev Drive (ReFS) mounted at `<workspace>/target` (`samypr100/setup-dev-drive`), its VHDX on the fixed volume with the most free space (a step picks it and prints every volume; the default `D:` is the workspace drive and fills first), and a step after the tests prints the volumes again. The `changes` job makes the macOS and Windows legs skip their steps (the job still runs and reports Success, so the check names stay) on a PR that touches only `website/`, `marketing/`, `docs/`, root-level `*.md`, `docs.json` or `.mintignore`; the Linux leg always runs everything, because Rust tests read the site and the docs. Never gate `build` with a job-level `if:` or a `paths:` filter: a skipped matrix job reports one unexpanded check name and a path-filtered workflow leaves required checks Pending. A main-branch run gets its own concurrency group (the run id) so a later push cannot cancel it while it is pending. Tauri bundle is intentionally NOT in CI (too slow); release workflows cover that.
- `auto-release.yml` fires off CI's `workflow_run` on main: tags `v<version>-dev.<run_number>` (e.g. `v0.3.0-dev.N`) and dispatches `release-dev.yml`.

## Separate workflows

Each of these is its own workflow so that a failure there can never turn the "CI" run `auto-release.yml` waits on red.

- `audit.yml` (workflow `Audit`) runs `cargo audit` on `Cargo.lock` weekly, on dispatch and on PRs that change `Cargo.lock` or a `Cargo.toml`; a vulnerability fails it, unmaintained/unsound/yanked crates only warn. It is a separate workflow, not a `ci.yml` job, so a new advisory can never fail the "CI" run `auto-release.yml` waits on. Clear a red one by bumping the crate (`cargo update -p <crate> --precise <version>`), never by adding an `ignore`; the `cargo-audit` version is pinned in the workflow's `CARGO_AUDIT_VERSION`.
- **Third-party notices** (`apps/desktop/src-tauri/licenses/THIRD_PARTY_NOTICES.txt`, generated and committed, bundled in every installer through `bundle.resources`, shown in Settings → Account → Open source licences by the `third_party_notices` command). Rust crates by `cargo-about` (pinned 0.9.2, cross-checked against `cargo tree` per target, because it drops a crate now and then; `scripts/third-party-notices/about.toml` is the allow-list of licences and the `clarify` entries, `about.hbs` the template), the JavaScript bundle by `rollup-plugin-license` (`EDYTLAB_NOTICES_JSON`, off in a normal build), and `credits.txt` by hand (the code the Rust crates were derived from, the models, the test data). A dependency under a licence outside `accepted` (GPL, LGPL, EPL, unknown) makes the generator fail: stop and ask the owner, do not add it. **Every dependency change, a Dependabot bump too, needs `node scripts/third-party-notices/generate.mjs` run and the file committed**: `notices.yml` (workflow `Notices`, apart from `ci.yml` for the reason `audit.yml` is) runs it with `--check` on PRs and pushes to main that change `Cargo.lock`, a `Cargo.toml`, `pnpm-lock.yaml`, `apps/desktop/package.json`, `vite.config.ts`, anything under `apps/desktop/src/`, the generator's inputs or the file, and weekly; `installer-ml-runtime.py check` fails an installer without the file. New code derived from a third-party project goes in `credits.txt` (with its licence text) and starts with a comment naming the upstream, its licence and copyright, and what changed. How each FOSSA obligation is met: "Third-party licences" in `docs/development-guide.md`.
- `ml.yml` (workflow `ML`) runs the tests CI cannot, on Linux with `--ignored`: the real whisper-base model on the pinned ONNX Runtime (`ml-whisper`'s `transcribe_known_words` and `transcribe_smoke`, plus the lib test that a decoder step does not copy the key-value cache (#657), `tools`' `transcribe_end_to_end` and `transcribe_load_errors`) and the real download (`ml-pipeline`'s `model_real_download`), and the speaker model (`ml-diarize`'s `real_model`, and `tools`' `diarize_end_to_end`: the `diarize` tool on the same AMI excerpt through `load`, two speakers, no node, a cache hit the second time, #168). It is opt-in: `workflow_dispatch` only (`gh workflow run ml.yml --ref <branch>`), never on push, a PR or a schedule, because it downloads ~139 MB of model and the runtime, and it is a separate workflow so a failure can never turn the "CI" run `auto-release.yml` waits on red. The runtime and the model are cached by the hash of their manifests; `scripts/fetch-ml-runtime.sh` and `scripts/fetch-ml-model.sh` run on a cache hit too and re-download what no longer matches the pin, so a damaged cache costs a download, not a wrong result. `crates/tools/tests/ml_workflow.rs` pins all of it (and runs the model script against a damaged folder). A new ignored model test goes in the workflow in the same PR as the test.
- `docs.json` at the root publishes `docs/` and `GLOSSARY.md` to Mintlify; `.mintignore` decides what is public (everything else, and `docs/specs/`, `docs/superpowers/`, `docs/brand/`, `docs/saas-evaluation.md`, `docs/archive/`, `docs/agents/`, stay private). A new published doc goes into `docs.json` `navigation`, is valid MDX (no HTML comments, no bare `<` or `{` outside code) and takes its title from `title:` front matter, not a `#` heading; Mintlify never publishes a file named `README` or `CONTRIBUTING`, so those stay GitHub-only. `docs/tools-reference.md` is generated: its escaping lives in `tools_reference_doc.rs`. The `Docs` workflow (`docs.yml`, apart from `ci.yml` for the reason `audit.yml` is) runs `mint validate` and `mint broken-links` at a pinned version.

## Releases

- To cut a versioned release: follow Release day in `CLAUDE.md`. The release is Latest, not a prerelease, and carries all six installers.
- `release-dev.yml` uses a `create-release` job + matrix to avoid the parallel-job race that produced duplicate releases for the same tag.
- Both release workflows ship the ONNX Runtime (#383): each leg runs `scripts/fetch-ml-runtime.sh` (and `scripts/installer-ml-runtime.py stage-vc-runtime` on Windows), builds with `--config src-tauri/tauri.ml-runtime.<os>.conf.json`, and runs `scripts/installer-ml-runtime.py check` on every installer before uploading it. Never put the runtime in `tauri.conf.json` itself: tauri-build fails on a resource that was not fetched. `release-dev.yml` gives tauri-action no `releaseId` (it would upload before the check) and uploads in its own step; `crates/tools/tests/release_ml_runtime.rs` pins all of this. To try a release build on a branch, dispatch `release-dev.yml` there with `dry_run: true`: it builds and checks, keeps the installers as a workflow artifact, and creates no tag or release.
- `release-dev.yml` has a `channel` dispatch input: `dev` (default — prerelease, not Latest, "unsigned dev build") and `release` (a real versioned release, not a prerelease, marked Latest). Tag pushes are always `dev`; a bare `vX.Y.Z` tag deliberately does not trigger it, so `release-signed.yml` owns those tags once certs exist. Both channels emit the same install warnings, because those describe the artifact rather than the channel.
- Signed releases (`release-signed.yml`) are manual `workflow_dispatch` and require Apple/Windows signing secrets. Same `create-release` + matrix + `publish` shape as `release-dev.yml`. tauri-action is given neither `tagName` nor `releaseId` there — it only builds, and upload happens after signing, so unsigned artifacts can never reach the release.
- Bundle targets are explicit in `tauri.conf.json`: `["app", "dmg", "msi", "nsis", "deb", "appimage"]`. Keep the list: `"all"` silently dropped installer formats under some build conditions.
