# LLM providers and the keychain

Read before touching a provider, the tool list a request carries, the session block in the system prompt, or a keychain or provider-settings slot.

## Providers and the tool set

- Multi-provider LLM support: Anthropic, OpenRouter, OpenAI, Groq, Gemini and Ollama (local, no key), and the ChatGPT plan (`chatgpt`, #474: Sign in with ChatGPT; Settings has its card (PR 6) and the site and privacy copy name it (PR 7); it shipped in v0.9.0 as a preview; see the ChatGPT bullets below). The `LlmProvider` trait in `crates/ai/src/provider.rs` is the extension point — request serialization + SSE parsing are per-provider. So is how much of the tool list a request carries (`tool_set()`): Ollama sends `ToolSet::Slim` (`crates/ai/src/tool_selection.rs`: a core list plus the tools the message names, the assistant just proposed or the user named earlier, compacted, within a byte budget, picked once per turn, with the names of the rest in one line of the system prompt so the model knows they exist, space-separated and a run of five sharing a first word written `prefix_{a,b,…}`; when the session block had to be cut, `list_session` is pinned into the set outside the tool budget, so the model can page through what the block left out, #618); every other provider sends all permitted tools, and Anthropic must, for its prompt cache. `crates/ai/tests/request_size.rs` bounds the slim request and ratchets the full one's system and tool sizes (`cargo test -p ai --test request_size -- --nocapture` prints them).

## The session block

- The session block in the system prompt (`crates/ai/src/session_context.rs`: head, tracks, buses, master chain, selection, markers) is written within a byte budget (`block_budget`, #573): `SESSION_BLOCK_MAX_BYTES` (8,000 B) for a provider sent every tool, `SLIM_SESSION_BLOCK_MAX_BYTES` (2,300 B) for Ollama, whose block also shares the request with the tools (what it takes past `SLIM_SESSION_ALLOWANCE_BYTES` comes off the slim tool budget). A session that fits is written in full. One that does not has its track, bus and marker lists cut, and each cut list ends with a line that says how many were left out and names `list_session` (`crates/tools/src/tool/list_session.rs`, read-only so Plan first never holds it), which pages through the same lines: `tools::session_lines` writes them once for both, so the block and the tool cannot disagree (#618, #634). `crates/ai/tests/request_size.rs` runs a thirty-track and a two-hundred-track session and holds every session's first request `SESSION_HEADROOM_BYTES` under the bound, so a change that grows the block, a tool schema or the names line moves those numbers: run it.

## Keychain and provider settings

- Provider slots live in two homes (#734, ADR 0009; `crates/ai/src/keychain.rs`). **Secrets** — `<provider_id>_api_key` for each hosted provider and `chatgpt_refresh_token` (the sign-in's refresh token, `ai::keychain::try_load_chatgpt_refresh_token` and its `save_` / `delete_`) — are the entries of ONE keychain item (service `app.edytlab.desktop`, account `secrets`, a JSON map from slot name to value). It is read once per process and cached, and every save and delete first reads the item itself again (a second process may have changed it), then updates the item and the cache together under the one lock that also serialises all keychain I/O, so a key save and a token refresh cannot lose each other. The item is written as UTF-8 bytes (`set_secret`), the reserved entry `__migrated` marks a finished migration (a marked item is never overridden by a leftover per-slot item), a kernel-keyring copy is merged into the durable item key by key, a failed (`PlatformFailure`) read is remembered for ten seconds (or until a save), and an MCP `<keychain:slot>` that is not a provider id is read on demand from the user's own `<slot>_api_key` item. The reason: macOS asks for the login password once per existing item an app reads when the item's access list does not name that exact build, and the installers are ad-hoc signed (#386), so every update is a new build; one item is at most one prompt per launch (and one Secret Service unlock on Linux, #527). **Non-secrets** — `active_provider`, `<provider_id>_model`, `<provider_id>_base_url`, `<provider_id>_effort` (the ChatGPT plan has no key or base-URL slot: it has `chatgpt_model` and `chatgpt_effort`) — are in `provider-settings.json` (`{ "version": 1, "active_provider", "providers": { "<id>": { "model", "base_url", "effort" } } }`) in the app config dir, written as a temp file renamed over the old one, never holding a secret, and a save of one makes no keychain call and answers `Durable`. `ai::keychain::set_settings_dir` registers that dir once (absolute path only, first call stands, like `ml_pipeline::runtime::set_bundle_dir`), in `lib.rs` setup before anything reads the keychain; until it is called every `ai::keychain` function answers with an error (the CLI never reads the keychain; a test registers a temp dir, or builds a `Store` over fake `Slot`s as `keychain_layout_tests.rs` does). A new slot goes in `Field` (`is_secret` picks its home), never as an item of its own. The slot names are the per-slot accounts earlier builds used (Anthropic's is `anthropic_api_key`), which is what the migration reads: when `provider-settings.json` is missing, the first call reads each legacy item, writes the `secrets` item, reads it back, writes the file (last, so its presence means the migration finished), reads it back, and only then deletes the legacy items it found. Any failure keeps every legacy item and the process runs on them as before (the `Legacy` layout), with the next launch retrying; a migration also waits while the Secret Service cannot be reached or when the new item could only be saved to the kernel keyring, and a refused read is the caller's answer and asked for again. A secret's `serde_json` parse error is never kept (it quotes the value). On Linux the store is the Secret Service (GNOME Keyring, KWallet or KeePassXC), with the kernel keyring as the fallback for the current boot only when none is running; `get_keychain_persistence` reports which applies and the app shows a banner (#394). `has_api_key` rejects when the keychain cannot be read — that is not the same as `false`. The commands that write a slot (`set_api_key`, `set_api_key_for`, `set_active_provider`, `set_base_url_for`, `set_effort_for`, `set_active_model`) answer with the same `{ persistent, reason }` for the save they made, so a service that went away after launch is not silent: Settings shows the banner's text (`lib/keychainNotice.ts`) and holds the dialog open on **Continue** (#539). After a startup the keychain refused (`AppState::keychain_refused`), `rebuild_agent_into` makes no keychain read and builds no agent until a key or provider save lifts the refusal; `send_message` says why.
