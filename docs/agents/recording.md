# Playback, recording latency and punch-in

Read before touching playback, microphone capture, latency calibration or punch-in.

## Playback

- Playback runs in the webview: WaveSurfer plays the rendered preview mix through an HTML media element (WebKitGTK's GStreamer on Linux). There is no native playback path — #388 removed the unused `audio-io` crate and `play_state`; the only native audio I/O is `crates/recorder` (cpal): microphone capture, and, since #203, one cpal output that plays a single in-memory buffer while the microphone is recorded on the same process clock (`duplex::play_and_capture`). It plays only the latency calibration's test sweeps and, while punching in (`punch_record`, #203), the monitor; the monitor is native so that it and the capture share one process clock, which the webview player (another process, a start delay that changes from run to run) cannot give. It is not a player, so nothing else may route playback through it, and the window pauses WaveSurfer before it asks for a punch.

## Recording latency

- **Recording latency (#203; `crates/recorder`, decisions on the issue's 2026-10-26 comment).** How late the microphone hears what the computer plays is measured, never guessed, and kept per device pair. The model (`latency.rs` docs): cpal's `StreamInstant` counts from an origin of each stream's own (ALSA: the stream's trigger or creation), so two streams cannot be related by their timestamps; each callback reads `Instant::now()` instead, and `Envelope` keeps the lower envelope of `t_callback - frame/sr` (scheduling only makes a callback late), warm-up skipped, with `AtomicI64::fetch_min`. Monitor frame `k` is captured at input frame `(k/sr + (P0 - C0) + L) * sr_in` (`input_frame_for`); `L` is the one constant per pair (buffers, converters, USB or Bluetooth, the air). The callbacks never lock, allocate or log (`duplex.rs`: the capture is a preallocated `Vec<AtomicU32>`; a stream error sets `xrun` and the caller refuses the take; so does `Envelope::lost_frames`, because a sound server behind ALSA's `default` hides its xruns and WASAPI playback reports none (ALSA, CoreAudio and WASAPI capture do report theirs since cpal 0.17 / 0.18.2, and any error the callback is handed refuses the take): after the warm-up it keeps the upper envelope of `t_callback - frame/sr` as well as the lower, and a spread of more than one buffer period (read from the callbacks) plus 20 ms means audio was lost; a shorter loss is not seen), every stream is opened through `recorder::stream_config`, which on ALSA asks for 50 ms periods (cpal keeps two: a 100 ms buffer), because cpal 0.18's own two device periods (about 5 ms each behind PulseAudio) underran 1 to 3 of the loopback's 5 tests on a busy machine and 50 ms passed 15 of 15 (CoreAudio and WASAPI keep their defaults; changing the buffering means a new `STREAM_SETUP`), and the streams are built and dropped on the calling thread, which waits for the whole take, so call it from a blocking task. `calibration.rs` plays five sweeps at irregular gaps (so a missing sweep cannot be mistaken for a late one), three runs, finds them by FFT cross-correlation (`locate_all`, confidence = peak over the correlation's RMS away from it, noise alone peaks near 5, the threshold is 12), and refuses unless all five are heard in each run and every estimate is within 1 ms (`CalibrationError`, whose text is shown to the person); the runs are separate because a run's sweeps share its clock estimate, so only separate runs show it moving. The refusal is by what the microphone heard, not by whether headphones are plugged in (cpal cannot tell). The pair's names come from `identify.rs`: cpal's ALSA host calls both default devices `default` (and lists `pulse` and `pipewire`) whatever they route to, so on ALSA those names become `default (<sink>)` and `default (<source>)` from `pactl get-default-sink` / `get-default-source` (run with a 2 s timeout; no libpulse dependency), and when the sound server cannot say, `default_pair` is `RecorderError::DeviceUnidentified` and nothing is measured or stored, with the reason in the Settings row. `store.rs` keeps `{latency_ms, spread_ms, measured_at, source: measured|manual}` per `host|output|input|out_sr|in_sr|cpal18` in `~/.edytlab/audio-latency.json` (the last field is `duplex::STREAM_SETUP`: a cpal change to the buffers moves the latency, so it gets a new value and entries under an older one, measured or typed, read as not measured) (temp file renamed; entries are kept as raw JSON and read one at a time, so one unreadable entry reads as not measured and a save writes every other entry back unchanged; a file that is not JSON at all reads as empty, a newer `version` is refused and left alone). Commands: `get_recording_latency`, `calibrate_recording_latency` (progress `{kind: "calibrate_latency", run, runs}` on the tool-progress channel, not on `ToolProgressBar`'s allow-list: the Audio tab's row reads it) and `cancel_recording_latency`. The measurement's Cancel is its own flag (`recorder::gate::GATE`), never `tools::progress`'s, which is the agent's `batch_apply` and `timer_record`: neither command may call `progress::begin`, `cancelled` or `request_cancel` (a test reads their text). The same gate makes a measurement, `start_recording` and an armed `timer_record` exclude one another (`start_recording` checks with its recorder slot locked; a measurement takes the gate and then looks at the slot), and the Audio tab's row cancels a measurement when it unmounts.

## Punch-in

- **The punch-in (#203 PR B; `crates/recorder/src/punch.rs`, `apps/desktop/src-tauri/src/punch.rs`, decisions on the issue's 2026-10-26 comment).** `punch_record { track, start_sec, end_sec, preroll_sec = 2, postroll_sec = 1 }` (pre- and post-roll at most 30 s, a region at most 300 s) refuses unless the default pair has a stored latency of **either** kind, `measured` or `manual`, with `PunchError::NotCalibrated`'s text naming both ways out in Settings → Audio (no default number: a guess is the silent lateness this exists to prevent); `set_recording_latency { latency_ms }` keeps a typed delay (0 to 2000 ms, `LatencyStore::put_manual`, `source: manual`, no spread, the newest write wins) and the Audio row has the field. `punch::run` (off the locks but for the steps below, on a blocking thread, behind an `Audio` trait so tests fake the devices) reads the head under the store lock (state, `materialize` first, then the track's `tools::track_take_format`: the rate of its clips and the channel count from a WAV's header), then renders over `[start - pre, end + post)` **twice** under the engine lock (`render_range_to_wav_cancellable`: Cancel is read at every block, and the engine lock is let go before the WAVs are read, #875) (the mix as it is, and a clone of the state with the track `muted` **and not soloed**, because a solo overrides a mute in `graph::build`; the clone is never stored, so no node; a muted render the renderer refuses with `InvalidRange`, because nothing else reaches the region, is silence), and `recorder::punch::build_monitor_from_wavs` streams them into one speaker-format buffer, using the first outside the region and the second inside it with a 5 ms amplitude crossfade (the renders share every other track, so gains summing to one leave it untouched; equal-power would lift it 3 dB) at each edge, in the speakers' rate and channels (`convert`: N to 1 averages, 1 to N copies, otherwise the first channels, for a mix; FFT resampler with its delay taken out). <!-- coderabbit-ai-generated:v1 --> Nothing is locked while the take is recorded. `extract` cuts the region at `input_frame_for` (frames before the capture are zeros; a capture that ends before the region does, a `xrun`/lost-frames capture and a missing output origin are refused, never padded or spliced around), `convert_take` puts it in the track's clip rate and channels **by what the microphone delivered** (`take_channel_map`: to mono the loudest channel by RMS; to several channels, when exactly one input channel carries signal and the rest are 40 dB or more below it, that channel on all of them; otherwise the first channels), the region is cut at the frames `punch_in` truncates to (`region_frames`) for the monitor, the capture and the tool alike, and the take is stored in the project as a float WAV named by `audio_hash` in `.audiograph/clipboard/` (`store_clipboard_blob`, like a pasted clipboard: the node records `punch_in` with that path as `reproducible`, so a replay after the history sweep finds it; a temporary file would not survive) and applied with `punch_in` through `run_track_tool_at_project`, which checks the weakly captured live-store identity against the open project and checks the head **in the same hold of the store's lock** the tool runs in; the project slot is released after the identity check, so a later switch cannot redirect the edit; a head that moved, a failure, or a cancel pressed after the take means it is **not** applied and (but for the cancel) the take stays in the project, its path in the error. **Cancel is its own flag in the gate** (`begin_punch` / `cancel_punch` / `punch_cancelled`, command `cancel_punch_record`), for the reason the measurement's is: `tools::progress`'s switch is the agent's `batch_apply` and `timer_record`, and a Cancel meant for a batch must not throw away a take with a performer in the room, nor the reverse (neither punch command may call `progress::begin`, `cancelled` or `request_cancel`; a test reads their text). The punch, a measurement, `start_recording` and an armed `timer_record` exclude one another through the same gate (each side sets its own flag and then reads the other's). Progress is `{kind: "punch_record", phase: preparing|preroll|recording|postroll|applying, remaining_sec}`, on `ToolProgressBar`'s allow-list; the bar keeps **one strip per kind** (a batch, a transcription and a punch-in may run at once: each strip's reports, Cancel and `done` are its own, and a `done` for a kind with no strip is nothing), the punch's Cancel calls `cancelPunchRecord` and is not offered in `applying`, and the command sends `done` only if it sent a report. The Punch button is also off while a scheduled recording is armed (`punchDisabledReason`). The window: the Punch button next to ⏱ (`lib/punch.ts`: on with a selection and a track, off while recording or punching), a popover with the track, the lead-in and the latency line ("Not calibrated — Settings → Audio" keeps Start off), WaveSurfer paused first, the new head adopted inside `inOrder` (the long wait is outside it). Drift between the two devices is parts per million of the take (about 3 ms in 30 s at 100 ppm): fine for a line, and the popover says so over 60 s. `crates/recorder/tests/loopback.rs` (`#[ignore]`; fails without `EDYTLAB_AUDIO_LOOPBACK=1`) is the stop rule: calibrations of three runs agree within 1 ms and the stored `L` predicts a fresh run's sweeps within 1 ms while `L = 0` misses by more than 5 ms; the same file holds the punch-in's, where the loopback is the performer: the take cut out for the region is the muted monitor's own region at a lag of 0 within 1 ms (0.0 to 0.2 ms measured), and cut without the latency it is late by the latency (33.4 ms on the private daemon with cpal 0.18, 75.6 ms with 0.15). The plain nominal splice (the capture's own seconds, no clock model) is only reported there, because on a loopback the device's buffer can cancel the latency by luck. `scripts/audio-loopback.sh` runs it on a **private** PulseAudio daemon (own socket, state and runtime dir under a fresh temp dir, one null sink, killed by PID on exit; never `pkill -f`, never the shared `demo` sink, and it refuses to start while `recording.lock` exists); `PULSE_SERVER` / `PULSE_SINK` / `PULSE_SOURCE` steer ALSA's pulse plugin, which is cpal's `default` device. It proves the clock model on a real device path; it cannot prove real converters or the air, which only a calibration on the user's machine measures.
